================================================================================
Enable Edge Engine — ビン（グループ）定義ロジック解説
================================================================================
最終更新: 2026-04-28

本ドキュメントは、スクリーニング処理において各ファクターの値をどのように
「ビン（グループ）」に区切っているかを日本語で解説するものです。

================================================================================
■ 「ビン」とは何か（基本概念）
================================================================================

ビン（bin）とは、ファクターの値を意味のあるグループに集約した「区画」です。

例: tansho_odds (単勝オッズ) を以下のビンに分けると…
  ビン A: 1.0〜2.9倍 → このビン内の馬の補正回収率を計算
  ビン B: 3.0〜4.9倍 → このビン内の馬の補正回収率を計算
  ビン C: 5.0〜7.9倍 → …

3-COMBOや4-COMBOの場合は、3〜4個のファクター値の「組み合わせ」が1ビン。
  例: (goal_juni="1位", kyori="1800", bac_jouken="A") → これが1ビン

補正回収率CLBは「ビン間の一貫性」を評価する指標であり、
  CLB = mean(全ビンのROI) - 1.96 × std(全ビンのROI) / √K
  K = 有効ビン数（BIN_MIN_N以上のサンプルを持つビン）

ビンのサンプル数が少ないと結果が不安定になるため、
最小サンプル数 (BIN_MIN_N) 未満のビンは評価から除外されます。

================================================================================
■ BIN_MIN_N の役割と設定値
================================================================================

BIN_MIN_N（有効ビン最小サンプル数）
  定義: ビンを「有効」と見なすための最小ベット数（馬券購入回数）
  設定値:
    スクリーニング本体: BIN_MIN_N = 100（factor_3combo_screening.py）
    OOT評価:           OOT_BIN_MIN_N = 30（factor_3combo_filtering.py）
      ※OOTはデータ期間が2023〜2025の3年分のみなのでより緩めの閾値

  影響:
    BIN_MIN_N が大きい → 安定したビン評価（外れ値影響↓）だが有効ビン数↓
    BIN_MIN_N が小さい → 有効ビン数↑だが個々のROI推定が不安定

MIN_VALID_BINS（有効ビン最小数）
  定義: CLBを計算するために必要な有効ビンの最低個数
  設定値:
    スクリーニング本体: MIN_VALID_BINS = 3
    OOT評価:           OOT_MIN_BINS = 2
    サブセット(クロスゲイン): min_bins = 2

  影響:
    MIN_VALID_BINS未満 → そのファクター×セグメントはスキップ（skip=True）
    3-COMBOで有効ビン3個以上 = 統計的に最低限の多様性が確認できる

================================================================================
■ ファクター種別ごとのビン区切り方
================================================================================

【種別1: カテゴリカル変数 (type=code)】
  対象ファクター例:
    keibajo_code    競馬場コード (01〜10)
    kyakushitsu     脚質コード (逃/先/差/追)
    hizume_code     蹄鉄コード
    moshoku_code    毛色コード
    shirushi_code_* 印コード (◎○▲△×★)
    bac_jouken      出走条件コード
    taikei_dou      馬体胴コード

  ビン区切り方:
    値がそのままビンになる（区切り不要）。
    例: shirushi_code_1 = {"◎", "○", "▲", "△", "×", "★", "（なし）"} がそれぞれ1ビン
    NULL・空文字・"nan" は無効扱いで除外。

  3-COMBOでの例:
    (shirushi_code_1="◎", shirushi_code_2="○", bac_jouken="500万以下") → 1ビン
    → そのビン内の馬が100頭以上いれば有効ビンとしてROI計算

【種別2: JRDBデータ由来の数値指数 (type=numeric)】
  対象ファクター例:
    idm             JRDBデータマイニング指数
    sogo_shisu      総合指数
    ten_shisu       テン指数（序盤の速さ）
    agari_shisu     上がり指数（終盤の速さ）
    pace_shisu      ペース指数
    kishu_shisu     騎手指数
    chokyo_shisu    調教指数
    kyusha_shisu    厩舎指数

  ビン区切り方: pd.qcut（等頻度分割）
    コード: labels_arr, bin_edges = pd.qcut(valid[col], q=NUM_BINS, ...)
    NUM_BINS = 10（10分位数による等頻度10分割）
    例: agari_shisu の値域を10等分 → 各ビンに全体の約10%のデータが入る

    補足: 等頻度なので各ビンのサンプル数は均一化される。
    値が全て同一（分散ゼロ）の場合は有効なビンが形成されない（duplicates="drop"）。

  生成されるビン:
    例: agari_shisu が 10〜100 の場合、0〜10%, 10〜20%, ..., 90〜100% のパーセンタイル区切り
    実際の区切り点は各セグメントのデータ分布に依存（固定幅ではない）。

【種別3: 順位ファクター (_juni 系)】
  対象ファクター例:
    goal_juni       ゴール時点順位（着順 = 実質的なカテゴリ値）
    ls_shisu_juni   LS指数の馬群内順位
    agari_shisu_juni 上がり指数の馬群内順位
    ten_shisu_juni  テン指数の馬群内順位
    dochu_juni      道中順位
    kohan_3f_juni   後半3F順位
    yoso_juni       予想順位
    kijun_ninkijun_tansho  JRDB基準単勝人気順位

  ビン区切り方: 整数値そのままビン（カテゴリカルと同様）
    goal_juni は 1, 2, 3, 4, 5, ... という整数値
    → 各順位がそのままビンになる（区切り不要）
    例: goal_juni=1（1着）のビン / goal_juni=2（2着）のビン / ...

    補足: 出走頭数が少ないレース（例: 5頭立て）では高順位ビンが形成されにくい。
    頭数変動のため一部の順位ビンはサンプル不足になりやすい。

【種別4: 距離・コース系】
  対象ファクター例:
    kyori           レース距離（1200, 1400, 1600, 1800, 2000, 2200, 2400, 3000, 3200等）
    kyori_kubun     距離区分（"短距離", "マイル", "中距離", "長距離"）
    course_27       コース複合キー（競馬場_芝ダ_距離区分の27通り）

  ビン区切り方:
    kyori: 実際の開催距離値がそのままビン（例: 1600m, 1800mはそれぞれ別ビン）
    kyori_kubun: 固定閾値による4区分
      短距離: kyori <= 1400m
      マイル: 1401m〜1799m
      中距離: 1800m〜2199m
      長距離: 2200m以上

【種別5: 馬体重系（派生ビン）】
  対象ファクター例:
    prev1_bataiju_bin   前走馬体重（20kgバケット区切り）
    bataiju_change_bin  馬体重変化量（±10kgバケット区切り）

  ビン区切り方: 固定幅バケット（floor関数）
    prev1_bataiju_bin:
      計算式: (prev1_bataiju // 20) * 20
      例: 468kg → 460kgバケット / 472kg → 460kgバケット / 480kg → 480kgバケット
      生成値: 400, 420, 440, 460, 480, 500, 520, 540, 560 (kg単位)

    bataiju_change_bin:
      計算式: ((当走馬体重 - 前走馬体重) // 10) * 10
      例: -4kg → -10kgバケット / +7kg → 0kgバケット / +12kg → +10kgバケット
      生成値: -40, -30, -20, -10, 0, +10, +20, +30 (kg単位)

【種別6: コーナー通過順位（派生ビン）】
  対象ファクター例:
    prev1_corner4_bin   前走4コーナー通過順位（グループ区分）

  ビン区切り方: 固定区間4グループ
    "1-3"  : 4コーナーを1〜3番手で通過（先行・逃げ）
    "4-6"  : 4〜6番手（好位）
    "7-9"  : 7〜9番手（中団）
    "10+"  : 10番手以降（後方）

【種別7: 騎手・調教師ランク（派生ランク）】
  対象ファクター例:
    kishu_rank      騎手ランク
    chokyoshi_rank  調教師ランク

  ビン区切り方: 5分位数による5ランク
    計算式: stats["win_rate"].quantile([0.2, 0.4, 0.6, 0.8])
    勝率の0%, 20%, 40%, 60%, 80%, 100% パーセンタイルで5グループに分割
    ランク1 (最下位) 〜 ランク5 (最上位) に分類

【種別8: オッズ系】
  対象ファクター例:
    tansho_odds_numeric     単勝オッズ（1.1〜100.0倍）
    kijun_odds_fukusho      JRDB基準複勝オッズ（1.10〜72.00倍）
    kijun_ninkijun_tansho   JRDB基準単勝人気順位（整数）
    kijun_ninkijun_fukusho  JRDB基準複勝人気順位（整数）

  重要な仕様:
    tansho_odds は DBに整数×10で格納（例: "80" = 8.0倍）
    → tansho_odds_numeric = tansho_odds / 10.0 に変換
    有効範囲: 1.0〜100.0倍（この範囲外は除外）

  使用場面:
    補正ROI計算: kijun_odds_fukusho をbet_amount計算の分母に使用
    Filter2 (印逆張り): tansho_odds_numeric >= 閾値 OR kijun_ninkijun_tansho >= 閾値

【種別9: 年度系】
  対象ファクター例:
    yy_int          年度（整数、例: 23 = 2023年）

  ビン区切り方:
    整数値がそのままビン（2016=16, 2017=17, ..., 2025=25）
    OOT分割: yy_int >= 23 をOOT期間（検証期間）として使用

================================================================================
■ 3-COMBO / 4-COMBO でのビン形成の仕組み
================================================================================

3因子(f1, f2, f3)の組み合わせでビンを形成する場合:

  グループキー = str(f1値) + "\x01" + str(f2値) + "\x01" + str(f3値)

  例: goal_juni=1, kyori=1800, bac_jouken="500万以下"
  → グループキー = "1\x011800\x01500万以下"

  numpy で np.unique(key_arr, return_inverse=True) を使って高速グルーピング。
  同じグループキーを持つ行が同一ビンに属する。

  ビンの有効判定:
    そのビンのサンプル数 >= BIN_MIN_N(=100) → 有効ビン
    BIN_MIN_N未満 → 除外（ビン数Kにカウントされない）

  4-COMBOでは:
    グループキー = str(f1) + "\x01" + str(f2) + "\x01" + str(f3) + "\x01" + str(f4)
    → 4次元なのでビンがより細分化され、サンプル不足になりやすい
    → これがBIN_MIN_N=100維持による「自然な絞り込み」として機能する

■ 各ファクターの値の意味（主要ファクター）
================================================================================

goal_juni       : その馬のゴール時点での着順（整数: 1=1着, 2=2着, ...）
goal_sa         : ゴール時点での着差（先頭馬との差: 0=1着相当, 正=劣る）
dochu_juni      : 道中順位（レース中盤での馬群内位置）
kohan_3f_juni   : 後半3F（最後の600m）での馬群内上がり順位
agari_shisu_juni: 上がり指数の馬群内順位（数値小 = 上がりが速い）
yoso_juni       : JRDBの予想順位（事前予測の馬群内順位）
pace_yoso       : JRDBのペース予想コード (H/M/S等)
prev1_bataiju_bin: 前走馬体重を20kgバケットで区切ったグループ
kijun_ninkijun_fukusho: JRDB基準複勝人気順位
kijun_ninkijun_tansho : JRDB基準単勝人気順位
bac_jouken      : 出走条件コード（クラス分け）
kyori           : レース距離（メートル整数値）
shutoku_shokin_ruikei : 獲得賞金累計（分位数ビン化される連続値）
kyi_kyusha_rank : KYI厩舎ランク
manken_shirushi : 万馬券印コード
shirushi_code_* : 各新聞印（◎○▲△×★）の印コード

================================================================================
■ OOT評価でのビン形成の違い
================================================================================

OOT（Out-of-Time、2023〜2025年）のビン形成は本体と同じロジックだが、
データ期間が3年分に限られるため:

  OOT_BIN_MIN_N = 30（本体100より緩めの最小サンプル数）
  OOT_MIN_BINS  = 2 （本体3より緩めの最小ビン数）

  → 時間的に独立したデータでの性能確認が目的なので、
    やや緩い閾値で過剰な排除を防いでいる。
  → OOT_CLB >= 75% の水準を要求することで、
    訓練期間(2016-2022)への過学習をフィルタリングする。

================================================================================
■ クロスゲイン評価でのサブセットビン形成
================================================================================

クロスゲイン = combo_clb - max(サブセットCLB)

サブセット（単独ファクター3個 + ペア3個）のCLB計算では:
  SUBSET_MIN_N = 100（本体と同じ最小サンプル数）
  min_bins = 2（最小ビン数）

サブセットのデータが全て不足 → cross_gain=None → 通過扱い
  （「独自性を否定できない」という保守的な判断）
